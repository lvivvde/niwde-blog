# AI 编程课：反馈循环、TDD、集成测试、模块与 Code Review 资料研究

## 结论先行

建议课程采用下面这条证据链，而不是把“多写测试”当成单一口号：

1. 先用可观察行为列出测试清单，再一次只把一个场景变成可运行测试。
2. 内层用短周期 Red–Green–Refactor 驱动行为和实现设计；外层用少量验收测试确认业务目标，用窄集成测试确认系统边界。
3. 反馈回路不仅要短，还必须可信：结果应稳定、失败应可诊断、失败原因应与当前修改相关。
4. 测试允许安全地改进结构；模块则通过信息隐藏，从源头减少调用者必须理解和验证的复杂度。
5. Code Review 不以“测试绿了”结束。评审者仍需核对目标、设计、边界、测试有效性和未覆盖风险，并让意见落在事实、数据或明确原则上。

下列 10 项来源均来自概念提出者、原作者、同行评审论文或官方工程实践。它们适合在课程 HTML 中以“观点 → 中文摘要 → 原文链接 → 适用边界”的形式出现。

## 来源与课程用法

### 1. Kent Beck：Canon TDD

- **出处**：Kent Beck, “Canon TDD”, 2023。原文：[newsletter.kentbeck.com/p/canon-tdd](https://newsletter.kentbeck.com/p/canon-tdd)
- **支撑的课程论点**：TDD 是一个行为驱动的编程工作流，不是“先一次性写完全部测试”。先列测试场景清单；一次只把一个场景写成可运行测试；让新旧测试全部通过；再选择性重构；重复直到清单为空。
- **中文摘要**：Beck 把 TDD 的目标写成四件事：旧行为仍工作、新行为符合预期、系统为下一次修改做好准备、团队对前三者有信心。测试清单属于行为分析，不应提前混入实现设计；具体测试主要推动接口决策，实现设计更多留到通过测试后的重构阶段。
- **建议在课上怎么用**：把它作为 Red–Green–Refactor 动画的权威主线，并在动画之前增加容易被遗漏的“测试清单”步骤。用一句醒目纠偏：**不是 Red–Green–Red，而是 Red–Green–Refactor；下一个 Red 开启下一轮。**
- **适用边界**：这是 Beck 对“规范 TDD”的定义和经验总结，不是证明 TDD 在所有团队、所有任务上都提高质量或速度的对照实验。重构在这篇表述中是“可选”，不应把每轮都必须产生结构变化讲成教条。

### 2. Martin Fowler：Refactoring（第二版官方页）

- **出处**：Martin Fowler with Kent Beck, *Refactoring: Improving the Design of Existing Code*, 2nd ed., 2018。官方页：[martinfowler.com/books/refactoring.html](https://martinfowler.com/books/refactoring.html)
- **支撑的课程论点**：重构是由一系列小的、保持可观察行为不变的转换组成；小步降低引入错误的风险，并让系统在结构改进期间保持可工作状态。
- **中文摘要**：Green 不是终点，而是安全整理结构的起点。测试的价值不只是证明刚写的功能能跑，还在于建立一条保护带，让开发者可以在不改变外部行为的前提下持续改善设计。
- **建议在课上怎么用**：解释为什么 TDD 的第三步不能长期省略，以及为什么“实现功能”和“改善结构”最好分戴两顶帽子。页面可展示同一轮中的两个检查点：功能刚通过、重构后仍通过。
- **适用边界**：“行为保持不变”依赖测试或其他观察手段覆盖了真正重要的行为；测试绿并不自动证明所有行为都未改变。性能、并发时序、日志和运维特征是否算“可观察行为”，需要由项目明确。

### 3. Steve Freeman 与 Nat Pryce：验收循环 + 单元循环

- **出处**：Steve Freeman & Nat Pryce, *Growing Object-Oriented Software, Guided by Tests*, 2009；作者官网开放的配图页：[growing-object-oriented-software.com/figures.html](https://growing-object-oriented-software.com/figures.html)
- **支撑的课程论点**：可以把测试驱动开发讲成嵌套的双循环：外层验收测试描述端到端能力，内层单元测试以更快的步幅驱动组成该能力的对象或模块。作者官网直接提供“TDD with acceptance- and unit-test cycles”图。
- **中文摘要**：外层回答“用户或业务目标是否实现”，内层回答“眼前这一小步如何可靠地实现”。外层测试先红并保持为方向标；开发在内层经历多轮 Red–Green–Refactor，最终让外层变绿。
- **建议在课上怎么用**：这是“反馈循环工程”章节的核心图。配合 Goal Brief，把成功标准转成外层验收示例，再把一个示例拆为若干内层行为测试。官网图使用 CC BY-SA 4.0，可在 HTML 中按页面要求署名后复用。
- **适用边界**：本书示例以面向对象、mockist TDD 为主；“外层验收 + 内层单元”是强教学模型，不是要求所有团队采用同样的对象划分、Mock 风格或工具。验收测试、集成测试、端到端测试并非同义词。

### 4. Martin Fowler：Integration Test

- **出处**：Martin Fowler, “Integration Test”, 2018（2021 更新）。原文：[martinfowler.com/bliki/IntegrationTest.html](https://martinfowler.com/bliki/IntegrationTest.html)
- **支撑的课程论点**：集成测试的核心是验证独立构建的单元连接后是否正确工作；它既可以是窄范围的边界测试，也可以是需要真实服务和网络的宽范围测试。窄集成测试通常更快、更稳定，能更早进入交付流水线。
- **中文摘要**：不要用“集成测试”这个名称替代测试设计。先说明要验证哪条边界、用真实依赖还是可信替身、失败可能意味着什么。游戏后端可把数据库 schema/ORM 映射、缓存协议、RPC 序列化、超时与重试分别放在窄边界测试中；只保留少量宽范围系统测试验证关键链路。
- **建议在课上怎么用**：用一张两列表对比“窄集成测试”和“宽系统/端到端测试”，让学员为同一风险选择最小、最快、仍有证明力的测试层级。
- **适用边界**：Fowler 明确提醒行业对 unit/integration 的定义并不统一。课程不应给出固定测试比例，也不应把所有使用替身的测试都叫单元测试。替身是否忠实本身还需要契约测试或针对真实实现的校验。

### 5. Noda、Storey、Forsgren、Greiler：DevEx 的反馈循环维度

- **出处**：Abi Noda, Margaret-Anne Storey, Nicole Forsgren & Michaela Greiler, “DevEx: What Actually Drives Productivity?”, *Communications of the ACM* 66(11), 2023, pp. 44–49。DOI：[10.1145/3610285](https://doi.org/10.1145/3610285)
- **支撑的课程论点**：反馈循环、认知负荷和心流是开发者体验的三个核心维度；开发者采取行动后，工具和人的反馈是否及时，是团队可以主动测量和改进的工作条件。
- **中文摘要**：循环工程不是“多跑几次 Agent”，而是设计从行动到可用反馈的时间与路径。对 AI 编程而言，测试、静态检查、构建、评审和真实运行信号都应尽量在开发者仍保有任务上下文时返回。
- **建议在课上怎么用**：用它为“为什么短反馈重要”提供研究框架，再让学员观察自己团队的 build、test、CI、review 等待时间，而不是只计算 AI 生成了多少代码。
- **适用边界**：这篇文章提出的是 DevEx 框架和测量方法，不能单独证明“把某个构建从十分钟降到一分钟就会带来固定比例的生产率提升”。课程应避免虚构量化收益，也不要把速度当成反馈质量的替代品。

### 6. Google Testing Blog：Flaky Tests at Google and How We Mitigate Them

- **出处**：John Micco, “Flaky Tests at Google and How We Mitigate Them”, Google Testing Blog, 2016。原文：[testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- **支撑的课程论点**：反馈必须同时及时和可靠。Google 的实践报告显示，不稳定测试造成大量误报、重复调查和延迟，并会让人习惯性忽略告警，进而漏掉真实失败。
- **中文摘要**：如果相同代码有时绿、有时红，Agent 和人都无法从失败中可靠地定位当前修改。这样的测试不仅慢，还会污染决策。可信循环要能区分代码回归、环境故障、第三方波动与测试自身缺陷。
- **建议在课上怎么用**：在“快 ≠ 好”页面展示信号矩阵：快且准最有用；快但噪声大导致误判；慢但准导致上下文切换；慢且噪声大应优先治理。配一个游戏后端例子：依赖真实时间、随机数或共享测试服数据的用例为什么会 flaky。
- **适用边界**：文中的具体比例来自 2016 年 Google 的超大规模测试体系，不能外推为一般团队的基准。它证明的是 flakiness 的成本和治理必要性，不证明某一种测试框架天然可靠。

### 7. David L. Parnas：按信息隐藏分解模块

- **出处**：D. L. Parnas, “On the Criteria to Be Used in Decomposing Systems into Modules”, *Communications of the ACM* 15(12), 1972, pp. 1053–1058。DOI：[10.1145/361598.361623](https://doi.org/10.1145/361598.361623)
- **支撑的课程论点**：模块化是否有效，取决于按什么标准拆分。围绕可能变化的设计决策做信息隐藏，比照着处理步骤或流程图切模块，更能提升系统的可修改性和可理解性，并支持并行开发。
- **中文摘要**：模块的重要性不在于“文件更小”或“类更多”，而在于变化能否被局部吸收。一个模块应隐藏某项容易变化的知识，让调用方只依赖稳定承诺。对 AI 生成代码尤其重要：如果规则、重试、存储与幂等细节泄漏到多个调用者，任何修改都要求 Agent 同时找全并正确更新这些位置。
- **建议在课上怎么用**：作为“为什么要有模块”的历史根基。展示两种拆分：按执行步骤散落活动奖励逻辑；按被隐藏的决策集中资格、幂等和发放策略。让学员判断哪种修改会扩散。
- **适用边界**：论文给出模块分解原则，不规定现代语言中的一个模块必须对应一个 class、package、service 或仓库；也不意味着所有变化都能被预测或所有耦合都能消除。

### 8. John Ousterhout：深模块与浅模块

- **出处**：John Ousterhout, *A Philosophy of Software Design*, 2nd ed., 2021；作者官方书页：[web.stanford.edu/~ouster/cgi-bin/aposd.php](https://web.stanford.edu/~ouster/cgi-bin/aposd.php)；配套课程讲义：[Modular Design](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php%3Ftopic%3DmodularDesign)
- **支撑的课程论点**：深模块用较简单的接口提供较多功能并隐藏较多信息；浅模块的接口复杂度相对它提供的能力过高，调用成本几乎接近直接实现。设计目标是让接口明显简单于实现。
- **中文摘要**：深度是“能力 ÷ 接口复杂度”的直觉比值，不是代码行数。一个奖励领取入口可以在内部承担资格判断、幂等、事务、失败归因和审计，却只暴露稳定的输入、结果与错误语义；相反，把每个步骤各包一层、迫使调用方理解正确调用顺序，仍然是浅设计。
- **建议在课上怎么用**：做同一能力的深/浅两张结构图，并给 Code Review 一个问题：**调用者为了正确使用它，必须知道多少内部决策？** 将“信息泄漏、转发方法、重复参数、过深调用栈”作为警示信号。
- **适用边界**：不要把“深模块”误讲成“大类最好”、单体最好或接口越少越好。接口还包含行为、约束、副作用和错误语义，不只包含方法数量；复杂实现如果不能被清晰维护，也不自动成为好模块。Ousterhout 的观点与部分“小类/短方法”传统存在有意分歧，适合用作评审镜头而非机械阈值。

### 9. Google Engineering Practices：Code Review 标准与检查项

- **出处**：Google, “The Standard of Code Review” 与 “What to look for in a code review”。原文：[评审标准](https://google.github.io/eng-practices/review/reviewer/standard.html)、[检查项](https://google.github.io/eng-practices/review/reviewer/looking-for.html)
- **支撑的课程论点**：评审判断应以技术事实和数据优先于个人偏好；评审范围包括整体设计、功能、复杂度、测试、命名、文档和系统上下文。测试本身也需要人检查是否正确、有效，是否会在代码破坏时真的失败。
- **中文摘要**：AI 可以系统扫描 diff，但绿色测试只是证据之一。评审者要核对“实现意图是否等于用户需要”，思考边界条件、并发风险、过度设计和对整体代码健康的影响，并在自己不具备安全、隐私、并发等专门能力时引入合格评审者。
- **建议在课上怎么用**：直接转成 Code Review Markdown 模板的栏目：目标/规格一致性、设计与模块边界、行为与边界条件、测试证据、回归与运维风险、不确定项与所需专家。要求每条阻断意见附上失败场景、测试结果、代码位置、规范或设计原则之一。
- **适用边界**：这是 Google 的内部经验公开版，不是所有团队必须原样采用的标准。它也没有宣称 Code Review 能证明程序正确；“看每一行”仍需结合变更风险和多评审者分工。

### 10. Bacchelli 与 Bird：现代 Code Review 的实际产出

- **出处**：Alberto Bacchelli & Christian Bird, “Expectations, Outcomes, and Challenges of Modern Code Review”, ICSE 2013, pp. 712–721。DOI：[10.1109/ICSE.2013.6606617](https://doi.org/10.1109/ICSE.2013.6606617)；开放存档：[Zenodo 记录与 PDF](https://zenodo.org/records/1401198)
- **支撑的课程论点**：对 Microsoft 多个团队的观察、访谈、问卷和评审评论分类显示，找缺陷虽是主要动机，但实际收益还大量来自代码/变更理解、知识传播、团队认知和替代方案；理解变更是评审的关键难点。
- **中文摘要**：Code Review 不应被讲成“再跑一次静态分析”或“让 AI 猜 bug”。评审首先需要足够上下文理解改动为何存在、如何融入系统，再讨论缺陷、设计和风险。AI 适合帮助整理调用者、依赖、测试和历史决策，但最终判断仍由理解业务与风险的人负责。
- **建议在课上怎么用**：为“AI 扫描、人做判断与负责”的分工提供实证背景。评审范本应先要求一段变更意图和影响面，再列发现；否则评论容易变成脱离上下文的风格偏好。
- **适用边界**：这是 2013 年 Microsoft 团队的探索性研究，不能直接量化今天使用 AI 评审的效果，也不能证明某种评审工具最好。论文观察到的是相关实践与认知，不是“评审一定能找到多少 bug”的保证。

## 三个需要在课程中主动纠正的二手简写

### “TDD 就是 Red–Green–Refactor”

这是方便记忆但不完整的简写。Beck 的规范描述还包含测试场景清单、一次只具体化一个测试、保持既有测试通过，以及对测试顺序的持续选择。课程可以保留三色循环，但应把测试清单放在循环之外作为入口。

### “测试金字塔规定了固定比例”

这些来源没有给出跨项目通用的比例。更稳妥的表述是：为每类风险选择最小但足够有证明力的测试；用大量快速、聚焦的反馈覆盖行为变化，用更少的宽范围测试守住关键旅程。先定义团队所说的“单元、集成、验收、端到端”，再谈组合。

### “测试都绿了，所以 Code Review 可以批准”

Google 的指南明确要求人检查测试本身是否有效，并继续审查设计、功能、复杂度、边界条件、并发和系统上下文。Bacchelli 与 Bird 的研究也表明，理解和知识传播是现代评审的重要结果。更准确的课程话术是：**绿灯说明已声明的检查没有发现失败，不说明声明完整，也不替代风险判断。**
