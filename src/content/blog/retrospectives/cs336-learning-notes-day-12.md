## 2026-11-08

### 今天的学习状态

后面的三讲，我只是大致听了一遍，并没有看得很懂。课程中有很多公式和训练算法，而我不是人工智能或神经网络相关专业的学生，也没有做过这方面的训练实践，因此不少内容暂时无法建立起清楚的理解。

下面主要借助课程资料，整理强化学习、多模态和推理系统的主线，方便以后复盘。这些笔记不代表我已经掌握了公式推导或实现细节。目前更重要的是先知道这些方法在解决什么问题，再在实践中逐步消化。

### 第十六讲：RLVR，用可验证的结果训练模型

#### 从“人更喜欢”到“结果是否正确”

上一讲介绍的 RLHF，主要通过人类偏好塑造模型行为。但人喜欢的回答不一定正确，奖励模型也可能存在偏差。一直追求更高奖励，有时会让模型学会迎合评分标准。

RLVR 的全称是 Reinforcement Learning from Verifiable Rewards，即“基于可验证奖励的强化学习”。它尝试在可以检查结果的任务上提供更明确的训练信号，例如检查数学答案是否匹配标准答案，或者运行测试判断代码是否正确。

它仍然会更新模型参数，只是奖励的来源有所不同。为了区分前面接触的概念，可以放在一起看：

| 方法 | 主要训练信号 | 可以怎样理解 |
| --- | --- | --- |
| SFT | 问题和示范回答 | 学习别人怎样回答 |
| RLHF | 人类偏好及据此得到的奖励 | 学习怎样回答更符合人的评价 |
| RLVR | 答案检查、测试等验证结果 | 学习怎样更容易完成可检查的任务 |

“可验证”也有边界：代码通过现有测试，不代表没有其他 Bug；数学最终答案正确，也不一定说明每一步推理都正确。验证器检查什么，训练就主要优化什么。

#### PPO 与 GRPO：怎样利用奖励更新模型

在语言模型中，可以把生成下一个 Token 看成一次动作，把生成回答的方式看成策略。模型生成完整回答后获得奖励，再用训练算法更新参数。

PPO 通常还需要一个价值模型，估计当前状态下预期能获得多少奖励。训练时比较实际结果和预期，判断哪些生成行为比预期更好。这部分会增加显存占用和训练复杂度。

GRPO 的一个关键简化是：对同一个问题采样多个回答，组成一组，在组内比较奖励，而不再单独训练价值模型。

例如，同一道题生成五个回答，其中两个答对、三个答错。算法可以根据它们相对于同组平均表现的差异，构造“优势”信号，指导参数更新。常见做法还会除以组内奖励的标准差进行归一化。

这里的“分组”是同一个问题生成的一组回答，与 MoE 把 Token 路由给专家不是一回事。如果一组回答的奖励完全相同，单靠这种组内比较就很难得到区分信号。

讲义还讨论了标准差归一化、回答长度归一化带来的偏差。我的理解目前停留在：这些看似很小的公式选择，会改变不同题目和不同长度回答在训练中的权重，并不是把奖励代入一个公式就结束了。

#### 长思维链与推理训练

课程通过 DeepSeek-R1、Kimi K1.5 和 Qwen3 等案例介绍推理训练。模型不仅生成最终答案，还可能生成较长的推理过程，也就是思维链（Chain of Thought，CoT）。

在一些训练中，模型会逐渐产生更长的推理过程，出现检查、反思和重新尝试等行为。但“想得更久”并不自动等于“想得更好”：长度增加可能与训练目标的偏差有关，一些看起来新出现的行为也可能已经存在于基础模型中。

这些案例的训练配方也各有不同：DeepSeek-R1-Zero 展示了直接从基础模型进行强化学习的效果；R1 则加入初始推理示范，以及后续 SFT 和偏好训练。Kimi 讨论了难度筛选、课程式训练和长度控制，Qwen3 讨论了思考模式与非思考模式的结合。

因此，实际训练可能反复组合 SFT、RL 和蒸馏，而不是严格地只按三个阶段各做一次。蒸馏则可以让强模型生成推理示范，再用于训练较小的模型；这与让小模型自己进行 RL 探索，是不同的学习方式。

#### 为什么强化学习训练还涉及系统工程

RL 训练需要反复生成回答、计算奖励和更新参数。生成回答称为 rollout，本身就是推理，尤其是长思维链会消耗很多时间。训练和推理还可能使用不同的执行框架，需要在两种工作负载之间切换。

同一批问题的回答长度也不同，较长的生成任务会拖慢整批处理。所以，强化学习算法是否有效，与它能否高效利用 GPU，是两个都必须解决的问题。

讲义最后还介绍了面向编程 Agent 的训练：构造代码仓库和任务环境，让 Agent 调用工具、修改代码，再依据执行结果训练。这里不仅需要题目，还需要能运行的环境、可靠的测试和足够丰富的执行轨迹。

这一讲先记住：RLVR 利用比较明确的结果反馈来训练模型，但训练效果仍然依赖基础模型、数据难度、奖励设计和系统效率。[课程讲义](https://github.com/stanford-cs336/lectures/blob/main/lecture_16.pdf)

### 第十七讲：多模态，让模型处理图像和视频

#### 图片怎样进入 Transformer

前面的语言模型主要处理文本，但真实世界还包含图片、声音和视频。要让 Transformer 处理它们，需要先把这些输入转换为模型能够使用的表示。

这里的视觉 Token 不一定像文本 Token 那样对应词表中的一个编号，也可以是一段连续向量。常见做法是将图片切成小块，用视觉编码器提取特征，再把这些特征交给语言模型。

所以，“让模型看图”并不一定要先把图片完整翻译成文字。图像本身的视觉信息就可以作为模型输入。

#### CLIP 与 SigLIP：让图像和文字建立联系

CLIP 使用图像和文字配对的数据训练两个编码器。在同一批数据中，让匹配的图文表示更接近，让不匹配的表示更容易被区分。

例如，一张猫的照片与“猫坐在椅子上”应该比与“汽车行驶在公路上”更匹配。这样得到的视觉表示能够反映图像语义，但 CLIP 本身不是一个完整的聊天助手。

SigLIP 改变了训练目标，将图文对是否匹配作为二分类问题，减少对整个批次一起做 Softmax 的依赖。这也会影响批量大小、显存和分布式计算的安排。

这部分把我之前接触的数据、向量和计算效率联系了起来：模型结构之外，训练目标的选择也会影响工程成本。

#### LLaVA：把视觉编码器接到语言模型上

LLaVA 展示了一种容易理解的结构：

> 图片 → 视觉编码器 → 投影层 → 语言模型 → 文字回答

视觉编码器先提取图片特征，投影层再将它们映射到语言模型可以使用的表示空间。训练时，可以先固定已有的视觉编码器和语言模型，只训练连接两者的投影层，再进行视觉指令微调。

这让我可以先从工程结构上理解多模态：复用已有模块，再训练连接部分，并不是所有能力都必须从零训练。

#### 高分辨率、视频和位置编码

把图片统一缩小、裁剪，虽然方便计算，却可能丢失小字、表格和边缘区域的信息。LLaVA-OneVision 等方案会将高分辨率图片拆成多个区域处理，但更高分辨率也意味着更多视觉 Token 和更高计算成本。

视频还多了时间维度。不能无限制地把每一帧、每一个像素都交给模型，因此需要在抽帧、分辨率、视觉 Token 数量和理解能力之间取舍。

Qwen-VL 系列的案例进一步讨论了动态分辨率和多模态位置编码。文本主要有序列位置，而图像有横纵位置，视频还有时间位置；MRoPE 把这些维度纳入旋转位置编码。Qwen3-VL 还使用显式时间戳，以及向语言模型多层注入视觉特征的方法。

此外，视频样本通常很长。如果训练损失只简单地按 Token 累加，长视频可能占据过大的权重，因此还要平衡不同模态的数据和训练目标。

#### 理解图像与生成图像，要求并不相同

识别“这是一只猫”主要需要语义信息，而生成图片还需要颜色、纹理、布局等细节。因此，适合理解的视觉表示，不一定同样适合生成。

讲义用 Chameleon 介绍了另一条路线：把图像编码成离散编号，与文本 Token 一起进行自回归建模，从而在统一序列中理解和生成图像。但离散化会丢失信息，多种模态一起训练也可能带来稳定性问题。

这一讲先记住：多模态不只是给语言模型加一个图片入口，还涉及编码方式、数据质量、位置表示、Token 成本和训练平衡。[课程讲义](https://github.com/stanford-cs336/lectures/blob/main/lecture_17.py)

### 最后一讲：Dan Fu 客座——推理系统与模型结构

这一部分结合讲者团队的公开研究资料整理，重点记录推理效率与模型设计之间的关系。

#### 模型训练完成后，还需要一套服务系统

训练得到模型参数，只是部署的起点。真正向用户提供服务时，还需要处理请求排队、批处理、缓存、GPU 调度、Token 采样和停止条件等问题。

这部分能与服务端经验联系起来：同样一份模型，放进不同的执行引擎和调度系统，延迟、吞吐和成本可能差很多。模型能力与服务系统的效率，需要分别考虑。

#### Prefill 和 Decode 的瓶颈不同

Prefill 是处理输入上下文，可以同时处理多个输入位置，通常比较容易形成高计算强度的矩阵运算。Decode 则逐步生成新 Token，尤其在小批量下，可能花很多时间读取模型权重和历史 KV Cache，更容易受显存带宽限制。

因此，推理优化不能只看显卡的理论浮点算力。还要看具体负载、批量大小、上下文长度，以及搬运的数据能否被充分复用。这也解释了为什么一些系统会把 Prefill 和 Decode 分开部署，但拆分后还要承担 KV 数据传输与调度的成本。

这些也是前面推理课程的基础概念，可以一起复盘。[推理课程讲义](https://github.com/stanford-cs336/lectures/blob/main/lecture_10.py)

#### Megakernel：减少 GPU 执行中的等待

一次模型前向计算通常由多个 GPU Kernel 组成，例如归一化、注意力和 MLP。Kernel 是在 GPU 上执行的程序；每次启动、收尾和同步都可能产生空隙，使 GPU 没有持续执行有效工作。

讲者团队的 Megakernel 研究尝试把整个小模型的前向计算融合进一个 Kernel，并安排加载与计算重叠，减少这些空隙。在小批量、低延迟的生成场景里，这种优化尤其值得关注。

但融合后需要自己管理更多依赖、同步和共享资源，实现难度也更高。这个研究案例让我可以先记住一个方向：单个算子已经很快时，算子之间的等待仍然可能影响整体速度。[Megakernel 原始研究说明](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)

#### Parcae：用参数复用增加计算深度

普通模型的不同层通常有各自的参数。循环模型则让中间状态反复经过同一组层，增加计算深度，同时复用参数。

可以粗略理解为：同一组处理模块多运行几次，每次继续变换上一次的中间状态。这不是重新提交同一个问题，也不是在推理时用 RL 更新模型参数，而是在一次前向计算中重复使用已有的层。

Parcae 研究的一个重点是训练稳定性。反复循环可能使中间状态不断放大，造成训练损失突增；作者通过调整和约束状态更新的方式，让这种结构更容易稳定训练。

它展示了通过增加循环计算来提高参数利用率的可能性，但更多循环仍然需要更多计算时间。参数减少也不能直接推出总显存一定同比减少，因为中间状态和 KV Cache 仍然占用空间。[Parcae 作者项目](https://sandyresearch.github.io/parcae/)

#### 从服务端角度理解这些取舍

在服务端系统中，连接池、批处理和缓存，都需要结合真实负载选择。大模型推理也类似：合适的批量、缓存复用和执行调度，要由请求特点和硬件条件共同决定。

例如，相同前缀可以通过 KV Cache 复用减少重复计算，但它要求前缀及其计算条件匹配，并不是两段内容“意思接近”就能复用。缓存也会占用显存，需要分配、引用管理和淘汰策略。[vLLM 前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)

这些联系能帮助我理解工程上的取舍，但 GPU Kernel、模型参数和 KV Cache 各自承担不同职责，不能直接套用服务器、数据库或 Redis 的全部机制。

### 这一轮先留下的理解

这三讲分别涉及怎样继续训练模型、怎样让模型处理更多类型的输入，以及怎样把模型高效运行起来。它们可以和前面学过的数据、矩阵运算、显存和缓存联系起来，但每一块都有很深的专业内容。

目前我没有理解透强化学习的梯度公式、优势估计，以及循环模型的稳定性分析，也还不能独立实现这些方法。这一遍更多是先建立印象：知道术语大致指什么、每种方法想解决什么问题。

以后做小模型或 Agent 实操时，可以再带着具体问题回来复盘。现在不把“听过一遍”当成“已经掌握”，也不需要为了记住全部公式而停在这里。
