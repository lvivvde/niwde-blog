## 2026-09-29

### Linear Attention、稀疏注意力与 DSA

#### 今天学到的内容与我的理解

今天先看了 Linear Attention，以及减少注意力计算量的一些方法。我的初步理解是：普通 Attention 会让序列中的 token 大范围互相计算，而一些新方法只计算局部区域或一部分位置，把原来很大的计算拆成更小的部分，从而提高性能。课程还讲到了一些门控机制，以及 DeepSeek 的 DSA；这部分公式较多，我目前主要处于接收状态，还没有深入理解。

#### AI 的整理与纠偏

- **Linear Attention 不等同于局部注意力。**普通注意力显式形成 `QKᵀ`，序列长度为 `n` 时，这个注意力矩阵有 `n²` 个位置。Linear Attention 会改写或近似注意力公式；在简化情形中，可以把 `QKᵀV` 改写为 `Q(KᵀV)`，先把历史信息汇总成固定大小的状态，再让 Q 读取这个状态。它的目标是让成本随序列长度近似线性增长，不一定只看附近 token。
- **只计算局部或少量位置，属于稀疏注意力。**滑动窗口注意力只看附近的一段上下文；块稀疏注意力按预定的小块计算；有些混合架构会交替使用局部层与全局层，以免长期信息完全断开。这更接近“把全量 Attention 拆成多个小区域”的理解。
- **如果课程中还出现了 FlashAttention，需要单独区分。**FlashAttention 也会把矩阵计算分块，但它主要是为了让数据更好地利用片上内存、减少显存读写；它通常仍计算数学上完整的 Attention，并没有因为分块就只看局部 token。
- **DSA 是 DeepSeek Sparse Attention，不是 DeepSeek Sparrow Attention。**DeepSeek-V3.2 的 DSA 使用一个较轻量的索引器，为当前查询从历史上下文中挑出较相关的 Top-K 位置，再只对这些位置执行主要的注意力计算。它属于动态、学习得到的稀疏选择，不只是固定滑动窗口，也不要求相关位置彼此相邻。
- **这里的“网关”更准确地说是门控（gating）。**在线性注意力或状态空间模型中，门控可以控制保留多少旧状态、写入多少新信息；它与互联网系统接收流量的 API 网关不是同一种组件。后面的 MoE 也有门控或路由器，但它控制的是 token 进入哪些专家。

一句话复盘：**Linear Attention 改变信息汇总方式，稀疏注意力减少实际参与计算的位置，FlashAttention 优化完整注意力的数据搬运，而 DSA 用学习到的索引器选择少量重要位置。**

### MoE：专家路由与分布式系统类比

#### 我的想法与疑问

MoE（Mixture of Experts，混合专家）让我想到互联网中的分布式架构。后端系统里的网关、数据库和业务服务器通常有明确职责；MoE 的专家却没有预先规定“负责代码”或“负责数学”。模型通过负载均衡把 token 分配给不同专家，因此专家之间的边界看起来没有传统服务那么明确。

我把 MoE 的路由器类比成负载均衡器：它预测一个 token 应该交给哪些专家。由此我产生了一个疑问：如果不同专家位于不同 GPU，它们怎样交换和保存数据？KV Cache 是否会像后端使用 Redis 一样，被放到一个所有专家都能访问的外部存储中？也许可以把一块 GPU 看作一台服务器，一块 GPU 上放置多个专家，再由系统调节专家的分布。

#### AI 的整理与纠偏

- **专家不是职责明确的微服务，也通常不是完整模型。**MoE 一般用多个专家 FFN 替换 Transformer 中原来的一个稠密 FFN；注意力、残差流、归一化等部分仍由模型共享。专家没有人工指定的业务标签，可能在训练中形成某些统计上的偏好，但这种分工是涌现出来的，不一定能清楚命名，也不保证长期稳定。
- **路由器与负载均衡器的类比只对了一部分。**路由器根据当前 token 的隐藏表示给专家打分，并选择 Top-K 专家；选中的专家输出再按权重合并。负载均衡机制的作用是防止少数专家过载、其他专家“饿死”。它通常约束一个批次或一段时间里的总体分布，并不是把每个 token 平均交给所有专家。路由首先要选合适的计算路径，均衡是附加约束。
- **专家之间通常不需要共享持久状态。**一个专家本质上是带参数的前馈网络，处理传入的 token 激活值并返回结果；信息继续随 token 的隐藏表示流向下一层。专家一般不直接读取其他专家的权重或“数据库”。在专家并行中，系统会把 token 激活值通过 GPU 高速互联发送到持有目标专家的设备，完成计算后再把结果发回并合并。这类 All-to-All 通信正是 MoE 多机训练和推理的主要成本之一。
- **KV Cache 不属于某个 MoE 专家。**KV Cache 由注意力层为每个推理请求保存，而 MoE 专家通常位于后面的 FFN 部分。token 被路由到远端专家时，传输的是该层的激活值，不需要把整份 KV Cache 一起交给专家。因此，不需要为所有专家建立一个类似 Redis 的共享 KV 数据库。
- **热 KV Cache 通常保存在 GPU 显存中。**高性能推理需要极低延迟和极高带宽，普通 Redis 或网络存储无法承担每生成一个 token 都要发生的大量读取。推理系统可以把暂时不用的 KV 块卸载到 CPU 内存或其他存储，也可以在请求间复用公共前缀，但再次使用前仍面临搬运成本。这是服务系统的内存管理问题，与 MoE 专家路由是两条不同的优化线。
- **把 GPU 看成计算服务器有助于建立直觉，但不能完全对应。**大模型通常分片到多块 GPU，一块 GPU 未必拥有完整模型参数；它可能保存一部分共享参数以及一个或多个专家。专家放置数量由显存容量、并行方案、通信拓扑和负载决定，通常在部署时规划，并不是每处理一个 token 就随意重新摆放。

可以把一次 MoE 层的过程简化为：`token 激活值 → 路由器选择 Top-K 专家 → 跨 GPU 分发 → 专家计算 → 返回并合并结果`。它与分布式后端都需要路由和负载均衡，但 MoE 传递的是高维张量，专家是同一神经网络中的可学习计算分支。

### 延伸思考：MoE 是否是分布式发展的必然结果？

#### 我的想法与问题

MoE 使用多块 GPU、路由器和负载均衡，让我进一步想到互联网服务端从单机走向分布式和集群部署的过程。当一台服务器无法承载全部业务时，就会增加机器并拆分负载；同样，大模型规模超过单块 GPU 的容量和算力后，训练与推理也必须扩展到更多设备。从这条发展路线看，两者似乎会自然走向相似的架构。

因此我猜测，MoE 可能会逐渐成为主流，甚至长期取代其他架构。不过我也意识到，自己经常把专家理解成“代码专家”“生活专家”等职责明确的分类。在真实训练中，专家并没有这样的人工标签，而且负载均衡还会尽量避免流量只集中到少数专家。

这又带来两个问题：如果真实用户长期只问代码或生活类问题，会不会只有少数专家被启用，大部分专家闲置？训练时又是怎样学习路由的——是按 token 做哈希，还是前向传播先选择专家，再在反向传播中像训练其他模型参数一样修改路由器？

#### AI 的整理与纠偏

1. **分布式扩展常常是规模增长的结果，MoE 却不是多 GPU 的必然结果。**模型太大时，参数、激活值和计算确实需要分布到多块 GPU；但稠密模型同样可以用数据并行、张量并行和流水线并行扩展。MoE 是另一层算法选择：让模型拥有很多专家参数，而每个 token 只激活少数专家，以较低的单 token 计算量换取更大的总参数容量。一个大型稠密模型可以跨很多 GPU，一个较小的 MoE 也可能放在一块 GPU 上。

2. **MoE 是重要方向，但还不能断言它会成为唯一架构。**当前许多高性能模型采用 MoE，说明稀疏激活的收益已经得到验证；与此同时，Dense、MoE 以及混合结构仍然共存。Qwen3 系列就同时包含稠密模型和 MoE 模型。最终选择还要看模型规模、训练数据、推理批量、延迟要求、硬件与通信成本。未来也可能出现新的条件计算或状态空间结构，因此“不会再有更好的架构”超出了现有证据。

3. **这版课程本身并不旧。**目前使用的官方页面标明为 Stanford Spring 2026，第四讲包含 Linear Attention、DSA 和近期 MoE 设计。我可能会看到旧论文或往年发展过程，但这份讲义已经把它们放进了 2026 年的架构脉络中。

4. **专家更像可学习的计算分支，不像人工划分的业务服务。**一个专家通常只是某层中的 FFN。训练可能让专家产生一定偏好，但模型没有保证某个专家只负责代码、数学或生活知识。不同层有各自的路由器；同一个请求中的不同 token、同一个 token 在不同层，都可能选择不同的专家。因此，一段代码对话通常也不会从头到尾只使用一个“代码专家”。

5. **大部分专家对单个 token 不启用，本来就是 MoE 的设计目标。**稀疏激活省下的计算，正来自每次只选择 Top-K 专家。真正的问题是整个批次或线上流量是否长期集中到少数“热门专家”，造成这些 GPU 拥堵，而其他 GPU 空闲。训练阶段会用均衡损失、路由偏置、容量限制或共享专家等方法减少塌缩；线上系统还可以通过批处理、专家副本、专家放置和调度缓解热点。训练时的均衡不能保证面对所有真实用户分布时仍然完美均衡。

6. **主流路由通常是学习得到的 Top-K，不是简单哈希。**路由器读取当前 token 的隐藏表示，通过一个很小的线性层或相似度计算得到每个专家的分数，再选择分数最高的 K 个专家。哈希路由可以作为简单基线，但难以根据上下文选择计算路径，不是当前主流大模型的主要方案。

7. **“前向选择，反向更新路由器”的理解基本正确，但有一个难点。**前向传播计算专家分数、执行 Top-K，并组合选中专家的输出；反向传播再根据最终损失更新专家和路由器参数。问题在于 Top-K 的离散选择不可微：选中路径可以获得梯度，未选中的专家通常得不到这次 token 的任务梯度。实际训练会结合可微的门控分数、均衡损失、随机扰动或路由偏置等启发式方法。课程说路由训练带有启发式色彩，主要就是指这个问题。

8. **模型先选择专家，专家放在哪块 GPU 是系统层的映射。**逻辑上，路由器决定 token 去哪个专家；物理上，专家并行会把不同专家放到不同设备。若目标专家在另一块 GPU，系统就把 token 的激活值通过高速互联发过去，再取回结果。负载均衡既要考虑专家获得的训练信号，也要考虑设备是否拥堵，但不能简单理解成“为了平均使用 GPU，随机把 token 分过去”。

#### Redis 类比可以保留到哪一层？

这个类比最有价值的部分，是**内存层级、局部性和通信成本**：互联网服务会把热点数据放到更快、更近的缓存；GPU 程序也会尽量让数据留在寄存器、片上缓存或显存中，减少反复经过较慢的链路。MoE 还会尝试减少跨设备 token 搬运，或者让路由集中在较少设备上。

但 Redis 与数据库并不是“先算 Redis、再算 MongoDB”的精确对应。Redis 通常承担缓存或快速状态访问，数据库承担持久化、查询和一致性；是否使用缓存取决于数据正确性、更新频率和访问模式。在大模型中，权重、激活值和 KV Cache 也分别有自己的生命周期，不存在一个能直接对应 Redis 的统一组件。MoE 甚至可能为了获得更大的参数容量而**增加**跨 GPU 通信，所以它同时利用了分布式扩展，也引入了新的搬运成本。

这个心智模型仍然很有用：两边都在解决“容量有限、计算节点增多、数据应该放在哪里、请求如何路由、怎样避免热点”的问题。复盘时只要把类比停留在这些共同原则上，不把专家、GPU、KV Cache 与微服务、服务器、Redis 一一绑定，就能帮助我同时理解两套系统。
