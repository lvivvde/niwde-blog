## 2026-09-27｜BPE 算法

### 学习内容

跟着课程学习了 BPE（Byte Pair Encoding，字节对编码）。它是一种把文本转换成 token 序列的分词方法：从字节（或具体实现采用的基础符号）开始，在训练语料中统计相邻 token 对的出现次数，反复合并最常见的一对，逐步构建子词词表。这样，常见片段可以用较少的 token 表示，少见内容仍能拆成更小的片段。

### 我的疑问与 AI 的纠偏

1. **BPE 的词表是针对每句话分别学习的吗？**

   **AI 的回答：**不是。训练 BPE 时，会在用于训练 tokenizer 的语料上汇总相邻 token 对的频次，再按合并结果生成一套共享词表和合并顺序。处理新句子时，使用这套已经学好的规则编码；不会为每句话重新造一套词表。实际实现可能先用正则等规则预切分文本，具体边界取决于 tokenizer。

2. **像 `th` 这样的片段本身没有完整词义，为什么要保留？遇到 `thank` 时，是优先匹配整个单词，还是拆成 `th`、`an`、`k` 等片段？**

   **AI 的回答：**token 不需要单独有词义。`th` 如果在语料中常见，就能作为多个词共享的片段，减少编码长度。`thank` 是否成为一个完整 token，取决于训练时是否通过连续合并形成了它；编码时按学到的合并顺序处理，不是简单地总选最长匹配或最短匹配。若完整词没进入词表，它仍可由更小的子词或字节表示。

3. **能否先按空格或符号切分语料、统计词频，把高频单词放进词表，再把低频词拆成字符？这种做法在词形变化、长尾词频和运行速度上有什么问题？**

   **AI 的回答：**整词加字符回退是已有的混合思路，可以工作，但有几项重要取舍：

   - **词形变化：**`thank`、`thanks`、`thanking`、`thankful` 如果都按整词收录，会占用多个词表位置。子词可以在不同词之间复用；但 BPE 按频次合并，不保证恰好切出真正的词根或词缀。`un-`、`-ing` 等片段的作用也需要模型从语境中学习，并非 tokenizer 直接赋予语义。
   - **长尾词频：**符合 Zipf 式分布的语料有大量低频**词种**，整词词表很难覆盖。低频词种占比很高，不等于它们占文本中**词次**的比例也很高；“超过 90%”取决于语料和低频阈值，不能当作通用数字。
   - **BPE 的区别：**它从字节或字符开始，反复合并全语料中常见的相邻片段；常见词可能成为一个 token，少见词可退回到共享子词或更小的单位。它不是先列出整词，再把词表外的词一律拆成单字符。
   - **速度：**按词查表可能让分词器本身更简单，但低频词拆成许多字符会增加模型要处理的 token 数。更长的序列占用上下文长度，标准全注意力的计算量还会随序列长度近似平方增长；更大的整词词表也会增加词嵌入和输出层的规模。实际运行速度要比较整个模型，而不能只看分词步骤。
