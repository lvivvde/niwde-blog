## 2026-10-05

### Scaling Laws：从规律走向实际训练配方

今天继续学习了 Scaling Laws 的第二部分。这一讲包含大量公式，也提到了学习率、batch size、初始化方式和优化器等内容。由于我之前接触这方面较少，目前主要先理解课程想解决的问题，不要求自己掌握每一步数学推导。

#### 这一讲在解决什么问题

上一部分更关注参数量、训练数据量和计算预算之间的规律；这一部分进一步讨论：真正把模型从小规模扩展到大规模时，其他训练设置应该怎样变化。

需要确定的内容包括：

- 模型应该多宽、多深；
- 模型参数量与训练 token 数应当怎样分配；
- 学习率和 batch size 应该怎样随规模变化；
- 初始化和优化器是否可以直接从小模型迁移到大模型；
- 怎样用较少的小模型实验，预测昂贵的大模型训练。

因此，这里的重点不是找到一个孤立的最优数字，而是得到一套 **scaling recipe**：输入计划使用的计算预算，就能推算模型大小、数据量和训练超参数。课程强调，可预测性有时和局部最优表现同样重要，因为一次大模型训练失败的代价非常高。

这里讲的“优化”主要指 **optimizer 和训练超参数优化**，并不是前面 GPU 课程中的算子或 kernel 优化。

#### MiniCPM 和 DeepSeek 的两种实践路线

课程首先分析了 MiniCPM 和 DeepSeek 的公开训练方法。

MiniCPM 先使用 **muP（Maximum Update Parametrization）**稳定不同模型宽度下的初始化和参数更新，希望在小模型上找到的学习率等设置可以迁移到大模型。随后固定模型的宽高比例，通过小规模实验拟合合适的 batch size、学习率以及数据量与参数量的比例。

DeepSeek 没有完全依赖 muP，而是直接训练多组小模型，搜索不同规模下较优的学习率和 batch size，再拟合它们随规模变化的趋势。对于模型大小和数据量之间的取舍，则继续使用类似 Chinchilla 的 IsoFLOP 实验：在相同计算预算下训练不同大小的模型，找出损失最低的配置，然后向更大的预算外推。

两种路线的共同思路是：先花较少成本探索小规模训练，再把规律用于真正的大模型。不同之处在于，MiniCPM 更依赖参数化方法保持超参数稳定，DeepSeek 更依赖实验搜索和经验拟合。

#### WSD 学习率为什么有用

传统的 Chinchilla 实验需要为许多“模型大小 × 数据量”组合分别从头训练，成本可能随实验规模快速增长。MiniCPM 和 DeepSeek 都采用了类似 **WSD（Warmup-Stable-Decay）** 的学习率计划：

1. Warmup：逐步提高学习率；
2. Stable：在较长阶段保持学习率稳定；
3. Decay：在训练末期降低学习率，让损失快速收敛。

这种设计允许研究者从 Stable 阶段的某个 checkpoint 分叉，再使用不同长度的 Decay 阶段得到多组训练结果。这样可以复用前面的训练过程，减少为拟合 Scaling Laws 而重复训练的成本。

#### 学习率和 Batch Size 也需要 Scaling

课程介绍的 StepFun 实验会在多个模型和数据规模上对学习率、batch size 做网格搜索。实验中，训练损失在这两个维度附近通常呈现比较清晰的低点，因此可以找到每个规模下的较优组合，再拟合变化趋势。

课程给出的经验是：较优 batch size 与数据规模的关系通常比较明显；学习率也可能随模型和数据规模变化，但更容易受到学习率计划、优化器和模型结构影响。换一个优化器之后，原来的学习率和 batch size 结论不一定继续成立。因此，比较不同优化器时，需要同时检查计算规模和模型与数据比例，不能只在一个小模型上比较一次。

课程还简要介绍了 Muon。它针对矩阵形式的参数处理更新方向，并使用 Newton-Schulz 迭代近似正交化。我的当前理解只停留在：优化器本身也会影响 Scaling 行为，不能默认一种优化器在小模型上的优势会原样延续到大模型。

#### muP 想解决什么问题

muP 的目标是让网络变宽时，模型内部数值仍处在相似的尺度：

- 初始化时，每层激活值的量级不要随着宽度增大而爆炸或消失；
- 完成一次参数更新后，激活值的变化也应保持在稳定量级。

为此，muP 会根据每层输入和输出宽度调整权重初始化以及学习率。直观上，它希望不同宽度的模型拥有相似的训练动力学，使小模型上找到的超参数能够迁移到大模型。

课程中的实验表明，muP 通常比标准参数化更稳定，但它并不是在任何配置下都自动成立。可学习的 RMSNorm gain、某些特殊优化器以及较强的 weight decay 都可能破坏这种迁移规律。这说明 muP 是降低调参成本的工具，仍然需要用实际实验验证。

#### 我的阶段性理解

这节课的大量公式，主要是在描述“模型规模发生变化时，各个量应该按什么速度变化”。现阶段不需要背下每个公式，可以先记住下面的工作流程：

1. 在多个较小规模上训练模型；
2. 分别搜索学习率和 batch size；
3. 在固定计算预算下寻找合适的模型大小与数据量；
4. 使用 muP 或经验公式，让超参数能够随规模迁移；
5. 使用 WSD 等训练计划复用计算；
6. 外推到目标规模，并检查最终损失是否符合预测。

我的宏观理解是：Scaling Laws 不只是在预测大模型能达到多低的 loss，也是在减少昂贵训练中的试错。它把“直接训练一个大模型”转化为“先用小规模实验设计一套可以外推的训练配方”。

### Evaluation：如何判断模型是否真的“更好”

课程接着介绍了 Evaluation，通常简称 **Eval**，也就是对模型或完整 AI 系统进行评测。这里最重要的结论是：不存在一种能够代表所有能力的统一基准。应该先明确自己想测什么，再选择与实际用途相符的测试。

#### 常见的评测类型

课程把常见评测大致分成以下几类：

1. **困惑度（Perplexity）**：观察模型给测试语料分配的概率。它适合衡量语言模型训练过程和 Scaling 趋势，但不一定直接反映模型能否完成现实任务。
2. **考试型基准**：例如 MMLU、MMLU-Pro、GPQA 和 Humanity's Last Exam。题目通常有明确答案，容易自动评分，也可以控制学科与难度。随着模型逐渐接近满分，研究者会继续增加选项、清理简单题或设计更难的新题。
3. **聊天基准**：真实聊天往往没有唯一正确答案，因此会让人类或另一个模型比较两份回答，或者按照评分标准判断回答质量。Chatbot Arena、AlpacaEval 和 WildBench 都属于这类评测。它们更接近真实使用，但容易受到回答长度、表达风格、评审偏好和讨好倾向影响。
4. **Agent 基准**：不只评价模型说了什么，还评价它能否使用工具、持续执行任务并得到正确结果。例如 SWE-bench 会提供真实代码仓库和 GitHub Issue，要求 Agent 修改代码，最终使用单元测试判断问题是否被解决。
5. **纯推理基准**：例如 ARC-AGI，尽量减少知识记忆的作用，通过每道都不同的图形规律题观察模型能否推导规则。它想把“记住过什么”与“能否对新问题进行推理”分开，但实际很难做到完全隔离。
6. **安全基准**：例如 HarmBench 和 AIR-Bench，检查模型是否会协助违法或有害行为，以及能否抵抗越狱攻击。安全本身与法律、文化和使用场景有关，因此也不能只依赖一个统一分数。

我最初提到“GPT-6 的纯推理应该已经超过 90%”，这个说法不够准确。模型只能在某个具体基准、特定版本和规定的测试条件下得到一个百分比。考试题达到 90% 不代表现实推理能力达到 90%；即使都叫 ARC-AGI，不同版本的难度和交互方式也不同。因此，文章不记录一个脱离基准名称和测试规则的笼统数字。

#### 为什么真实任务越来越重要

传统多选题有明确答案，成本低、易复现，但人们通常不会在现实中只让 AI 回答选择题。越接近真实使用的任务，评测越有意义，同时也越难控制变量。

SWE-bench 是一个典型例子。它不只询问一段代码怎么写，而是要求系统理解代码库、定位 Issue、编辑多个文件、运行测试并反复修正。最终结果由测试判断，因此比只评价模型生成的一段代码更接近真实软件开发。不过，测试用例本身是否充分，也会影响评测是否可信。

课程还提到了 Terminal-Bench、CyBench 和 MLE-Bench，分别关注终端操作、网络安全任务和机器学习工程。这些基准说明，同一个模型在不同真实环境中的表现可能相差很大。

#### Agent 的成绩不等于底层模型的成绩

课程给出的定义是：

```text
Agent = Language Model + Agent Scaffold
```

Agent Scaffold 是模型外部的执行框架，包括工具调用、任务规划、待办列表、上下文管理、文件记忆、失败重试和子 Agent 分工等逻辑。因此，同一个底层模型放进不同 Agent 框架中，最终得分可能有明显差异。

这不仅是编码能力的差异。编码任务最容易通过单元测试观察结果，但任何需要工具、记忆和多步执行的任务都会受到 Agent Scaffold 影响。因此发布 Agent 基准成绩时，需要说清楚评测的是裸模型、某种提示方法，还是“模型加 Agent 框架”的完整系统。

#### 基准测试本身也可能失效

一个 Eval 至少需要考虑三个方面：

- **难度**：测试过于简单时，大多数模型都接近满分，无法继续区分能力；
- **真实性**：题目是否接近用户真正会遇到的任务；
- **有效性**：分数是否真的测到了想测的能力。

有效性还会受到数据污染影响。如果模型在训练时已经见过测试题，高分可能来自记忆。真实代码基准也可能存在测试覆盖不足、Issue 描述含糊或任务本身无法稳定复现等问题。因此可以使用更新的题目、私有数据、内部代码库或更严格核验过的 benchmark，但这些方法又会增加成本并降低公开可复现性。

#### 我的阶段性理解

Eval 的作用不是简单地给模型排一个总榜，而是把“这个模型好不好”转换成一个可以观察的问题。评测结果必须和使用场景一起阅读：知识问答、聊天体验、代码修复、纯推理和安全性测量的是不同能力。

选择模型或 Agent 时，我更应该先问“它是否适合我要完成的任务”，再看与该任务最接近的基准，而不是只根据某个综合排行榜或一个百分比分数判断。
