## 2026-10-04

### Scaling Laws：用小规模实验推演大模型训练

#### 今天学到的内容与我的理解

今天主要学习了第 9 讲的 Scaling Laws，也就是缩放定律。这部分给我的感觉很像统计学：研究者会记录模型参数量、训练数据量、计算量、训练时间和最终表现，再分析这些变量之间的关系。

训练大模型非常消耗时间和资金，因此不可能为了尝试每一种配置，都完整训练一次大模型。更现实的做法是先训练一系列小模型，得到多组实验数据，再根据这些数据拟合规律，推演更大计算预算下应该选择多大的模型、使用多少训练数据。已有论文和其他模型的训练结果也可以作为参考。

课程中对一些数值取了对数。我目前不熟悉这里的数学推导，只大概理解为：模型表现与参数量、数据量和计算量之间存在一种比较稳定的规律，可以通过小规模实验估计未来大模型的表现，并寻找给定预算下更合适的训练方案。

课程还比较了 Kaplan 等人在 2020 年提出的缩放定律和 2022 年的 Chinchilla 论文。我的初步印象是，早期结论更强调增加模型参数，后来的研究发现不能只扩大参数量，还必须同时增加训练数据。这部分比较偏学术，我目前先理解它的整体思路。

#### AI 的整理与纠偏

**Scaling Laws 研究的是经验缩放规律。**常见变量包括：

- 模型参数量 `N`；
- 训练 token 数量 `D`；
- 训练计算量 `C`；
- 验证损失 `L`，有时也会观察下游任务表现。

研究者训练许多规模较小、配置受控的模型，观察这些变量如何影响损失，然后拟合经验公式。这样可以在真正投入巨额预算之前，估算不同配置可能得到的效果。

**这里通常说的是幂律（power law），不是多项分布。**简化之后，一项关系可能写成：

```text
L(N) ≈ A × N⁻ᵅ + L∞
```

它表达的是：参数量增加时，损失通常会继续下降，但边际收益逐渐变小。数据量和计算量也可以得到类似关系。这些规律来自实验拟合，并不是从数学上证明模型必然按照这条曲线发展。

**取对数是为了让幂律更容易拟合和观察。**如果忽略常数项，幂律可以写成：

```text
y = a × xᵇ
```

两边取对数后得到：

```text
log(y) = log(a) + b × log(x)
```

原本弯曲的幂律关系，在 log-log 图上会接近一条直线。这样就可以用相对简单的统计方法估计斜率和截距，再向更大的规模外推。

**使用别人的训练结果需要保证条件尽量一致。**公开论文、训练日志和已有模型可以帮助判断大致趋势，但不同项目可能使用不同的数据质量、tokenizer、模型结构、优化器和学习率计划。把这些数据直接放在一起拟合，可能把训练方案的差异误认为规模效应。因此，可靠的缩放实验通常会尽量固定训练方法，只改变少数目标变量。

#### Kaplan 与 Chinchilla 的差异

Kaplan 等人的 2020 年论文发现，语言模型的损失会随参数量、数据量和计算量呈现相对稳定的幂律变化。其计算最优结论更倾向于：在固定计算预算下，使用更大的模型、相对较少的数据，并在完全收敛前停止训练。

Chinchilla 团队在 2022 年重新进行了更大范围的实验，认为当时许多大模型其实训练不足。它给出的核心结论是：在计算预算增长时，模型参数量和训练 token 数应当更均衡地一起增加。论文中的 Chinchilla 模型有 700 亿参数，使用约 1.4 万亿 token 训练；它与 2800 亿参数的 Gopher 使用近似训练计算量，却在许多任务上表现更好。

因此，“参数越多就一定越强”并不准确。参数更多会增加模型容量，但如果计算预算固定，模型过大就意味着每个参数看到的数据太少，训练不充分。真正要寻找的是参数量、数据量和计算预算之间的平衡。

**这次变化并不表示 2022 年后稠密模型被 MoE 取代。**Chinchilla 研究的重点是稠密模型在固定训练计算量下，应该如何分配参数量和数据量。MoE 则通过每个 token 只激活部分专家，在总参数量和实际计算量之间进行另一种取舍。此后稠密模型和 MoE 模型都在继续发展，它们是两条可以并存的架构路线。

#### 如何用缩放定律制定训练方案

一种常见方法是：

1. 选择多个较小的计算预算；
2. 在每个预算下训练不同参数量和数据量的模型；
3. 找出每个预算下损失最低的配置；
4. 拟合最优参数量、数据量与计算预算之间的关系；
5. 将曲线外推到计划中的大模型训练预算。

这类实验可以显著降低盲目训练大模型的风险，但预测仍然有适用范围。模型结构、数据质量和训练方法发生变化时，原来的曲线可能失效；外推距离太远也会增加误差。另外，如果模型未来会被大量用于推理，训练阶段的计算最优方案也不一定是总成本最低的方案，因为较小模型通常拥有更低的推理成本。

#### 今天的整体理解

Scaling Laws 的价值不是证明“模型越大越好”，而是在训练成本极高的情况下，用一系列可承受的小规模实验估计大规模训练的趋势。它帮助研究者在参数量、训练数据和计算预算之间做出更有依据的选择，但最终仍是一套依赖实验条件的统计预测。

### Inference 与 KV Cache：初步理解

今天还学习了 Inference。由于内容是边看边口述的，前面的记录顺序和课程顺序并不完全一致。下面按照课程的四段结构重新整理：先理解推理工作负载，再讨论可能有质量取舍的优化，然后介绍无损的推测解码，最后处理在线服务中的动态请求。

#### 一、理解推理工作负载

##### Inference 是什么

这里的 Inference 就是“推理”：使用已经训练好的模型，根据输入计算并生成输出。训练阶段会通过反向传播修改模型参数；推理阶段通常只执行前向计算，不再更新参数。

对于自回归语言模型，一次推理通常可以分为两个阶段：

1. **Prefill**：一次性处理用户输入的 prompt，为所有输入 token 计算中间状态；
2. **Decode / Generation**：根据已有上下文逐个生成新 token。

所以，“从输入到输出的整个过程”这个理解是正确的，但从性能角度还需要把它拆成 prefill 和逐 token 生成两个阶段。

课程还区分了三个性能指标：TTFT 表示用户等待第一个 token 的时间，主要受 Prefill 影响；Latency 表示单个请求生成 token 的速度；Throughput 表示整个系统每秒能处理多少 token。增大 batch 往往能提高总体吞吐量，却可能增加单个请求的等待时间。

##### HBM 是什么内存

HBM 是 High Bandwidth Memory，也就是 GPU 使用的高带宽显存。它和 GPU 的计算单元放得很近，带宽远高于普通系统内存，常用于保存模型参数、激活值和 KV Cache。

它更接近通常所说的 GPU VRAM，而不是 Redis：

| 存储 | 位置与用途 | 是否天然跨进程或跨会话 |
| --- | --- | --- |
| HBM / GPU 显存 | GPU 直接进行高速计算 | 否 |
| 系统内存 / RAM | CPU 使用的主内存 | 否，除非程序专门共享 |
| Redis | 独立服务进程提供的网络化键值存储 | 是 |

HBM 只是一种硬件内存，并不自带 key、TTL、会话共享或持久化语义。推理服务进程负责决定哪一段显存属于哪个请求，以及什么时候释放。部分系统也可以把 KV Cache 临时转移到 CPU 内存或其他设备，但会付出额外的数据搬运成本。

##### H100：计算能力与显存带宽的关系

课程还用 H100 说明了为什么推理经常受显存带宽限制。判断一个操作受计算限制还是带宽限制，需要比较两个指标：

```text
算术强度 = 完成的浮点运算次数 ÷ 搬运的字节数
```

算术强度越高，表示每搬运一个字节的数据，可以完成越多计算；算术强度低，则表示数据刚被搬进来，很快就算完了，计算单元需要继续等待下一批数据。

课程中的简化 H100 示例使用了大约 `989 TFLOP/s` 的计算能力和 `3.35 TB/s` 的 HBM 带宽：

```text
989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOP/Byte
```

这个约为 295 的比值可以看作该示例中的硬件分界线：

- 工作负载的算术强度高于约 295，更可能受计算能力限制，也就是 compute-bound；
- 工作负载的算术强度低于约 295，更可能受显存带宽限制，也就是 memory-bound。

以矩阵乘法 `X × W` 为例，当隐藏维度远大于 batch size 时，课程把算术强度近似为 batch size `B`。训练或 prefill 可以同时处理许多 token，让同一份模型权重被重复使用，算术强度比较高；逐 token 生成时，每次只处理一个新位置，极端情况下 `B = 1`，算术强度接近 1，远低于 H100 示例中的 295。此时即使 H100 拥有很强的浮点计算能力，计算单元也会花很多时间等待模型权重和 KV Cache 从 HBM 搬过来。

Attention 的逐 token 生成更加明显。每生成一个新 token，都需要读取此前较长的 KV Cache，却只为当前 token 完成一轮 Attention。课程推导的生成阶段 Attention 算术强度小于 1，因此它通常是非常典型的 memory-bound 操作。

这也解释了为什么推理优化经常围绕显存展开：

- 量化模型参数，减少每次读取的字节数；
- 使用 GQA、MLA 等方法缩小 KV Cache；
- 通过 batching 让多个请求共同分摊读取模型权重的成本；
- 使用连续批处理和 PagedAttention，提高显存利用率。

增大 batch 通常可以提高总体吞吐量，因为一次读取的权重服务了更多请求；但每个请求都有自己的 KV Cache，batch 越大，显存占用和单个请求的等待时间也可能增加。如果超过 H100 的显存容量，就无法继续通过增加 batch 获得收益。因此，推理服务需要在延迟、吞吐量和显存容量之间取舍。

##### KV Cache 保存了什么

因果语言模型生成新 token 时，只能关注它之前的 token。前面每个 token 在每一层 Attention 中产生的 Key 和 Value 不会因为后面新增 token 而改变，因此可以把这些 K、V 向量保存起来。

生成下一个 token 时，模型只需要为新 token 计算新的 Q、K、V：新的 Q 与缓存中的全部 K 做 Attention，再读取对应的 V；新产生的 K、V 随后追加到缓存末尾。这样就不需要每生成一个 token，都重新计算整个前缀的 K 和 V。

KV Cache 的大小会随以下因素近似线性增长：

```text
序列长度 × 模型层数 × KV Head 数 × Head 维度 × 每个数的字节数 × 2
```

最后的 `× 2` 分别对应 Key 和 Value。并发会话越多、上下文越长，KV Cache 占用的显存就越大。

##### Prefill 和 Decode 的瓶颈为什么不同

我最初把 prefill 受计算限制理解为“输入数据还需要从外部搬进来”。这个原因并不准确：从外部读取请求当然需要时间，但课程讨论的核心是 GPU 内部的计算量与 HBM 数据搬运量之间的比例。

- **Prefill 通常偏 compute-bound。**一个 prompt 中的许多 token 可以同时组成较大的矩阵运算。同一批模型权重被大量 token 共同使用，每搬运一次数据便能完成很多计算，因此更容易把 GPU 的计算单元用满。
- **Decode 通常偏 memory-bound。**生成阶段每轮只为每个请求产生一个新 token，却仍要读取各层模型权重，并读取不断增长的 KV Cache。每次搬来的数据对应的计算较少，因此更容易受 HBM 容量和带宽限制。

这里的“真正推理”更准确地说是逐 token 的 Decode。Prefill 本身同样属于推理过程，只是两个阶段的工作形态不同。

#### 二、允许质量取舍的推理捷径

这一讲还有一个重要的分类：推理优化要区分是否会改变原模型的计算结果或输出分布。这里说的“有损”主要是模型质量或输出分布可能发生变化，不完全等同于浮点数位数所说的数值精度。

**可能有质量取舍的优化**包括降低权重或 KV Cache 的量化精度、丢弃一部分 KV Cache，以及只选择部分历史位置的稀疏 Attention。MQA、GQA 和 MLA 则通过共享或压缩 K、V 减少缓存；它们通常需要在模型设计或训练阶段使用，可能影响模型表示能力，但不能简单理解成推理时随机删掉了一部分答案。DeepSeek 的 MLA 也属于用更紧凑表示换取显存和带宽效率的架构选择。

**不改变原模型结果的系统优化**包括 KV Cache 分页、完全相同前缀的缓存复用、写时复制和连续批处理。只要实现正确，这些方法只是改变数据的存放和调度方式，不会改变模型原本执行的数学计算。

##### 通过架构减少 KV Cache

课程中出现的几个概念比较容易混在一起，它们减少开销的方式并不相同：

| 方法 | 核心做法 | 主要减少什么 |
| --- | --- | --- |
| MQA | 所有 Query Head 共享一组 K、V | KV Cache 和读取带宽 |
| GQA | 若干 Query Head 为一组，每组共享 K、V | KV Cache 和读取带宽 |
| MLA | 把 K、V 压缩成维度更低的潜在表示，需要时再恢复参与 Attention | KV Cache |
| Local / Sparse Attention | 只让当前 token 关注部分历史位置 | Attention 计算量和 KV 读取量 |
| Prefix Caching | 多个请求复用完全相同前缀的 KV Cache | 重复的 Prefill 计算 |

我听到的 DeepSeek“潜在多头注意力”应该是 **Multi-head Latent Attention（MLA，多头潜在注意力）**。MLA 的重点不是判断某句话有没有用，而是压缩每个历史 token 的 K、V 表示。这样仍然可以关注历史 token，但不需要为每个 token 保存那么大的 KV Cache。

我所理解的“给历史 token 打分，分数低的就不计算”，更接近 **稀疏 Attention**，而不是 MLA。以 DeepSeek Sparse Attention 一类方法为例，可以先用成本较低的索引器估计当前 Query 与历史位置的相关性，选择得分较高的一部分位置，再让主要的 Attention 只计算这些位置。这里被打分和筛选的是历史 **token 或位置**，而不是笼统判断一整件事是否重要。

例如，小明说了 A 到 G 七件事，当前生成内容可能主要与 A、D、G 有关。稀疏 Attention 会根据当前 Query 动态选择相关位置；B 在这一步分数较低，并不表示 B 永远无用。换一个问题或换一层网络时，被选中的位置都可能改变。

因此，这些方案可以分成两条思路：MLA、GQA 和 MQA 尽量缩小每个位置需要保存的 K、V；稀疏或局部 Attention 则尽量减少本次需要读取和计算的位置数量。它们也可以组合使用。

##### 量化、剪枝与蒸馏在课程中的位置

按照课程顺序，减少 KV Cache 之后还介绍了量化，以及通过剪枝和蒸馏得到更小模型。量化用更少的位数保存参数或激活值；剪枝移除相对不重要的层、Attention Head 或隐藏维度；蒸馏再用原模型帮助较小模型恢复能力。它们都用更低的推理成本换取速度，因此课程把这一组放在“可能有损的捷径”中。这里我目前只记录它们在整体脉络中的位置，具体算法留到后续理解。

#### 三、无损捷径：推测解码

课程后面介绍的无损加速方法应该是 **推测解码（speculative decoding）**。它使用一个速度更快的小模型作为 Draft Model，再用原来的大模型作为 Target Model：

1. 小模型先连续生成多个候选 token；
2. 大模型把这些候选位置作为一批，一次前向计算出每个位置的 logits；
3. 系统按照接受规则，从前往后验证候选 token；
4. 候选被接受时，一次便能向前推进多个 token；
5. 遇到第一个被拒绝的位置时，丢弃它后面的候选，并根据大模型的分布继续采样。

关键优势来自自回归生成的串行瓶颈：大模型原本每次只能生成一个 token，需要反复读取全部模型权重；现在由小模型便宜地提出多个候选，再让大模型利用并行计算一次验证多个位置。大模型仍然会为这些位置计算 logits，并不是只对小模型的整段回答给一个总分。

标准推测解码使用严格的接受与校正规则，使最终采样分布与直接使用大模型相同，因此可以称为无损。贪心解码时也可以接受连续匹配的候选，并在第一个不匹配处改用大模型的 token。某些工程实现为了更高速度会放宽验证规则，那些近似版本才可能改变输出分布。

这种方法确实存在合适的候选长度：

- **候选太少**：启动小模型、组织 batch 和调用大模型验证的额外开销，可能超过一次推进少量 token 带来的收益；
- **候选太多**：越靠后的候选越可能因为前面某个 token 被拒绝而一起作废，小模型生成它们的计算和大模型对它们的验证都会被浪费；
- **小模型太弱**：候选接受率低，经常只能前进一两个 token；
- **小模型太大**：候选更准确，但小模型本身已经不够快，抵消了加速收益。

因此，推测解码的效果取决于小模型速度、候选长度、候选接受率、大模型并行验证效率和具体硬件。目标不是让小模型代替大模型，而是用小模型减少大模型必须串行执行的 Decode 次数。

#### 四、处理动态的在线请求

前面的优化关注单次计算和模型结构，接下来处理在线服务中的动态问题：请求到达时间不同、输入和输出长度不同，而且部分请求拥有相同前缀。课程先讲连续批处理，再讲 PagedAttention。

##### 连续批处理：让多个聊天请求共同计算

网页聊天服务可以把多个用户当前要生成的 token 组成一个 batch，在 GPU 上并行执行。这里发挥大规模矩阵并行能力的主要是 **GPU**，CPU 更多负责接收请求、调度 batch 和启动计算。

普通的静态 batch 会等待整批请求全部结束。由于不同回答的长度不同，较短请求完成后仍可能占着位置。连续批处理（continuous batching，也称 iteration-level scheduling）会在每一轮 Decode 后重新整理队列：

1. 把当前仍在生成的请求组成 batch；
2. 在 GPU 上为每个请求各生成一个 token；
3. 移除已经生成 EOS、命中停止条件或达到长度上限的请求；
4. 将等待队列中的新请求加入空出的位置；
5. 继续下一轮生成。

每个请求仍拥有独立的 token 序列和 KV Cache，只是在某一轮计算时临时组成同一个 batch。PagedAttention 等显存管理方法让不同长度的 KV Cache 可以分块存储，连续批处理则负责决定每轮有哪些请求一起计算，两者经常配合使用。

这样做能让一次读取的模型权重同时服务多个请求，提高 GPU 利用率和总体吞吐量。不过，请求数量过多时，每个请求也可能等待更久，因此推理系统仍需要在吞吐量和单次请求延迟之间做取舍。

##### PagedAttention：按块管理 KV Cache

早期或简单实现确实可能在请求开始时，根据最大上下文长度和最大生成长度，预先分配一块连续显存。这种方式实现简单，但会出现两个问题：实际输出可能远短于预留长度，造成内部浪费；不同大小的请求反复申请和释放连续空间，还可能造成显存碎片。

现代推理系统常使用类似操作系统分页的方式，例如 vLLM 的 PagedAttention：

1. 服务预先维护一个由许多固定大小 block 组成的 KV Cache 显存池；
2. 每个请求先获得少量 block；
3. 随着 token 逐步生成，再按需申请新的 block；
4. 一张 block table 记录该序列的逻辑 token 位于哪些物理 block；
5. 请求结束后，相关 block 被释放并交还给池。

因此，它不需要一开始就为每个请求预留最大连续空间，也不要求一个会话的 KV Cache 在物理显存中完全连续。

如果缓存池不够，系统只能在几种策略之间取舍：限制新请求进入、让请求排队、暂停并稍后重新计算、把部分缓存转移到 CPU 内存、淘汰可复用的前缀缓存，或者拒绝超过显存与上下文上限的请求。KV Cache 不能无限增长，模型的上下文窗口和推理服务的显存预算共同决定了上限。

##### 分块共享、引用计数与写时复制

课程还介绍了 KV Cache 的分块共享。可以把一段序列的 KV Cache 切成固定大小的 block，例如用“每 4 个 token 一个 block”帮助理解。实际系统的 block 大小是实现参数，不一定固定为 4。

分块同时解决了两个问题：一方面，小块可以放进显存池中任意可用的位置，减少申请大块连续显存造成的外部碎片；另一方面，多个请求可以让自己的 block table 指向同一个物理 block，从而复用公共前缀。

例如，很多请求使用完全相同的 system prompt。只要它们经过相同的 tokenizer，并使用相同的模型权重、位置和推理配置，对应的 K、V 就相同，因此可以共享已经计算好的前缀 block。复用通常以完整 block 为单位；最后一个没有填满的 block 是否能够直接共享，要看具体实现。

**写时复制（copy-on-write）发生在共享内容需要被修改时。**两个请求可以先共同引用只读的前缀 block。后续 token 不同时，通常直接为各自的后缀申请新 block；如果仍要向同一个未填满的共享 block 追加内容，系统会先复制该 block，再让两个请求分别写入。这里并不是“采样到不同的 prompt”——prompt 是输入；更准确地说，是两个请求的 token 序列从某个位置开始出现分歧。

我的疑问是：同一个 block 被多个请求引用，系统如何知道它何时可以释放？这确实需要类似引用计数的机制：

1. CPU 侧的 block 管理器为每个物理 block 保存引用数或等价的占用状态；
2. 新的请求或分支开始共享该 block 时，引用数增加；
3. 请求结束、取消、报错或分支释放时，引用数减少；
4. 引用数归零后，block 可以回到空闲池，或者作为前缀缓存暂时保留；
5. 显存不足时，再按照 LRU、空闲时间或其他策略淘汰无人使用的缓存 block。

这个思路与 C++ 的 `shared_ptr` 很像，但实现不一定真的为每个显存块创建一个 `shared_ptr`。GPU 里的 block 主要保存 K、V 数值；引用计数、block table、空闲链表等元数据通常由推理引擎在 CPU 侧统一维护。使用普通整数引用计数和专用显存分配器，往往比通用智能指针更容易控制性能和批量调度。

引用计数归零和 TTL 解决的是不同问题：引用计数表示是否仍有活跃请求依赖该 block，不能错误释放；TTL 或 LRU 决定无人使用但可能再次命中的前缀缓存要保留多久。一个引用数仍大于零的活跃 block，即使超过五分钟也不能仅凭 TTL 释放。

如果取消请求、异常退出等路径没有正确减少引用数，确实可能造成显存泄漏。因此工程实现需要保证所有结束路径都会回收 block，并通过缓存容量上限、淘汰策略和监控兜底。这个风险需要被管理，但并不是分块共享无法解决的问题。

##### KV Cache 是否有 TTL

TTL 不是 KV Cache 本身的固有属性。一个正在生成内容的请求必须保留自己的 KV Cache；生成结束后，如果服务不准备复用这个前缀，就可以立即释放显存。

有些在线服务会继续保留已完成请求的公共前缀，以便后续相同 prompt 直接复用，这通常称为 prefix caching 或 prompt caching。这类缓存可以设置空闲超时、TTL、LRU 淘汰或其他回收策略。“五分钟后卸载”更可能是某个具体服务的缓存保留策略，并不代表所有 KV Cache 都有统一的五分钟 TTL。超时是否会在每次访问后刷新，也由具体服务决定。

因此，可以借用 Redis 的 TTL 和淘汰策略帮助理解缓存回收，但 KV Cache 通常仍由推理引擎直接管理在 GPU 显存中，并不是存入一个外置 Redis 服务。

##### 从某个历史节点 Fork，能否复用 KV Cache

如果原会话经历了：

```text
A → B → C → D → E → F → G
```

现在从 F 重新分叉并生成新的 G′，理论上可以复用 `A～F` 对应的 KV Cache。因为两个分支在 F 之前拥有完全相同的 token 前缀，它们在这些位置产生的 K、V 也相同。原来的 G 与新的 G′ 不同，因此从第一个不同 token 开始，需要分别计算和保存新的 KV Cache。

PagedAttention 一类系统可以通过引用计数和 copy-on-write 实现这种共享：两个分支先共同引用前缀 block；当各自继续生成时，只为不同的后缀申请新 block，不复制整段公共前缀。

实际能否复用还取决于推理服务是否实现并保留了这项能力。通常需要满足：

- 前缀 token 完全一致，位置也一致；
- 使用相同模型权重、tokenizer、适配器和相关推理配置；
- 前缀缓存尚未被释放或淘汰；
- 服务端能够识别共同前缀并共享对应 block。

如果只是在聊天界面上 Fork，但后端已经释放缓存，或者每次请求都被当成完全独立的无状态调用，那么界面虽然保留了相同文字，服务端仍然需要重新执行 prefill。

#### 当前阶段的整体理解

KV Cache 可以理解成推理过程中保存在 GPU 显存里的中间计算结果。它随着 token 逐步追加，由推理引擎负责分配、分页、共享和回收。它在概念上具备缓存的复用与淘汰特征，但没有 Redis 那样天然的跨进程、网络访问和 TTL 语义。

目前我能够先把这些优化按目标区分开：Prefill 和 Decode 的性能瓶颈不同；MLA、GQA 等方法缩小 KV Cache；稀疏 Attention 减少实际关注的位置；PagedAttention 管理显存块；连续批处理提高多个在线请求共同推理时的 GPU 利用率；推测解码则用小模型提出候选，让大模型并行验证，以减少大模型串行 Decode 的次数。后续还需要继续理解它们的公式和具体实现。
